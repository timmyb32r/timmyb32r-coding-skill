# Timmy Code Style

Пиши так, чтобы из кода были видны предметный алгоритм, владелец каждого
изменяемого состояния и порядок внешних эффектов. Дополнительные строки
оправданы, когда облегчают чтение. Дополнительные сущности и механизмы
требуют содержательной причины.

Это персональные предпочтения для нового и изменяемого кода. Учитывай язык,
соглашения проекта и явные указания пользователя. Не превращай применение
стиля в переписывание соседних модулей или изменение контракта задачи.

## Архитектура и модульность

### Выбирай сущности по реальному жизненному циклу

- Определи, чем владеет один экземпляр: одной задачей, документом, сессией
  или реальным набором объектов. Для одного объекта храни его напрямую.
  Не создавай registry, manager и map только ради потенциального будущего множества.
- Выделяй модуль вокруг самостоятельной ответственности: построение результата,
  работа с хранилищем, взаимодействие с внешней системой, управление жизненным циклом.
- Разные реализации нужны, когда различаются алгоритмы или контракты.
  Интерфейс должен выражать необходимую потребителю операцию, а не повторять
  все методы реализации. Не вводи интерфейс только потому, что появился struct.

### Делай зависимости направленными

- Вызывающий слой связывает компоненты и задаёт порядок работы. Алгоритмический
  модуль получает необходимые данные и зависимости, возвращает результаты.
- Не передавай весь service/controller/application ради доступа к двум полям.
  Не заставляй нижний слой обращаться обратно к верхнему владельцу через
  объект «текущего контекста».
- Сначала предпочти обычные аргументы и возвращаемые значения. Callback уместен,
  если эффект действительно нужен внутри алгоритма: обозначь, что он делает,
  когда вызывается и как ошибка влияет на дальнейшую работу.
- Общие данные, которыми обмениваются два модуля, не должны принадлежать одному
  из них только по исторической случайности. Размещай их в наименьшем подходящем
  месте; не создавай универсальную свалку `common` или `utils`.

### Назначай одного владельца состояния и ресурсов

- Владелец изменяет состояние и отвечает за согласованность. Остальные компоненты
  получают данные или вызывают содержательные операции владельца.
- Не подменяй временно `currentJob`, store или конфигурацию общего объекта
  с восстановлением через `defer`. Передай нужный объект явно либо создай
  отдельный экземпляр с фиксированной привязкой.
- Отделяй вычисление от сохранения и других внешних эффектов, когда это помогает
  видеть порядок. Явно показывай границу, после которой изменение становится
  внешне наблюдаемым. Не меняй необходимую атомарность ради красивого разделения.
- Изоляцию изменяемых данных обеспечивай на реальной границе владения.
  Копирование вложенных map/slice необходимо, если иначе наружу выходит
  изменяемая ссылка; копирование каждого значения на каждом вызове не является целью.
- Создание, передача и освобождение ресурса должны иметь понятного ответственного.

### Сокращай число фактов и уровней, которые надо поддерживать

- Перед добавлением поля проверь, не выводится ли оно из имеющихся данных.
  Избегай двух реестров одного объекта, кэша без причины и флага рядом с фактом,
  который этот флаг повторяет.
- Взаимоисключающие состояния выражай одним состоянием вместо независимых bool.
  Сохраняй отдельные поля для действительно независимых измерений.
- Убирай обёртки над срезом/структурой, алиасы и forwarding-слои, если они
  не обеспечивают отдельный контракт, инвариант или жизненный цикл.
- Не создавай отдельный пакет для внутренней детали единственного потребителя
  без причины. Инкапсуляция внутри пакета часто достаточна.
- Группируй методы вокруг владельца. Не разбрасывай одну сущность по множеству
  файлов `queries`, `commands`, `resources` ради одинаковой длины файлов.
  Отдельный файл предметной сущности и `*_funcs` для относящихся к ней функций
  допустимы; размер файла сам по себе не определяет архитектуру.

### Используй установленные гарантии внешнего контракта

- Перед защитным механизмом выясни, какие состояния достижимы на реальном пути
  вызова. Используй уже существующие гарантии порядка, завершения и повторов.
- Не строй новый протокол координации, журнал, fallback или lifecycle hooks
  для случая, уже исключённого действующим контрактом.
- Сохраняй проверки внешних данных, идентичности, ошибок и подтверждения эффектов,
  если они защищают реальную границу отказа. При неизвестной гарантии сначала
  проверь контракт; отсутствие проверки нельзя оправдать предположением.
- Не навязывай совместимость с собственными промежуточными черновиками.
  Выпущенные поддерживаемые контракты сохраняй согласно задаче и проекту.

## Обоснование корректности

- До реализации исправления определи предпосылки, от которых зависит его
  корректность. Неочевидные предпосылки проверь по официальной документации
  языка или API.
- Отличай документированную гарантию от поведения, наблюдаемого в тестах.
  Прохождение тестов не устанавливает недокументированную гарантию.
- Не определяй владение, валидность или идентичность по случайным деталям
  реализации, если их контракт явно не гарантирует такой вывод.
- Для unsafe-кода обоснуй выполнение предусловий каждой операции для всех
  входов, разрешённых публичным API, включая FFI-значения от внешнего кода.
- Если для корректности нужна информация, которую текущее представление
  не позволяет надёжно получить, измени её представление или учёт.
  Не подменяй отсутствующую гарантию эвристикой.
- Для изменений unsafe-кода, владения через FFI или выделения и освобождения
  памяти запускай релевантные тесты под Miri в дополнение к обычным тестам.
  Если Miri недоступен, явно сообщи о пробеле в проверке.

## Читаемость реализации

- Называй предмет и действие: `BuildReport`, `SaveDraft`, `WaitForJobsAndClearRecords`.
  Различай id/name/key, подготовленность/завершённость, локальный результат/сохранённое
  состояние. Имена map должны помогать понимать соответствие ключа значению.
- Сложные составные условия раскладывай на последовательные проверки.
  Сначала ранние выходы, затем основной путь. Не запрещай простые `for range`,
  `if` и `defer` там, где они и так прозрачны.
- Обработку значимой ошибки делай явной. Не меняй результат работы через
  `defer` или named return ради сокращения обычного пути. `defer` для освобождения
  ресурса уместен.
- Длинные вызовы, вложенные функции и литералы раскладывай вертикально.
  В Go предпочитай отдельное указание типа каждому параметру, явные конструкторы
  с обозримым начальным состоянием полей и предметные имена локальных переменных.
  Не прячь обязательные зависимости в дополнительный Config ради короткой сигнатуры.
- Комментарии объясняют смысл полей, предусловия, порядок действий, результат,
  различия режимов и причину необычного решения. Конкретный пример часто полезнее
  общего обещания надёжности. Поддерживай их соответствие коду.

## Как применять

При работе с модульными границами прочитай соответствующие примеры из
[references/before-after.md](references/before-after.md):
1 — размер сущности; 2 — направление зависимостей; 3 — владение состоянием;
4 — оправданность обёртки; 5 — модель состояний; 6 — layout модулей;
7 — имена и прямой поток выполнения.

До изменения установи единицу работы, владельцев и необходимые эффекты.
Это часть размышления над задачей, не обязательный отдельный документ или
повод останавливать реализацию.

Перед сдачей проверь:
- У каждой изменяемой сущности и ресурса понятен владелец?
- Можно понять направление зависимостей без обхода callback-цепочки?
- Каждый пакет, интерфейс и wrapper добавляет содержательную границу?
- Нет реестра для одного объекта, выводимого поля или дублирования состояния?
- В основном пути видны порядок эффектов и обработка ошибок?
- Не расширилась задача ради гипотетического будущего сценария?

Если упрощение ломает контракт или скрывает реальную сложность, сохрани
необходимый механизм и объясни его назначение. Краткость не является метрикой.
